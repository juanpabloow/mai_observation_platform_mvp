CONTRATO DE LECTURA

GET /api/handoff/v1/context
Parámetros obligatorios:
  workflow_ref: ID propio del workflow, no el del borrador QA.
  conversation_ref: la misma referencia opaca del push/gate.
  through_message_id: message_id devuelto por el push/gate para el mensaje actual.

Autorización: Bearer, permiso NUEVO handoff.context.read, opt-in.
handoff por sí solo NO permite leer el historial. No se añade al conjunto legacy
ni a los permisos predeterminados de tokens nuevos. Se edita desde Machine tokens
por owner/admin; no requiere emitir otra clave. No se ha concedido en producción.

Alcance: tenant + conexión del token + workflow + cliente no predeterminado,
Inbox habilitado + conversación + ancla de cliente recibida de esa conversación.
El cliente nunca viene de un parámetro del caller. Referencias de workflow
ambiguas entre conexiones/clientes fallan cerradas, porque conversations no tiene
connection_id. Un único SELECT da una fotografía consistente de modo e historial.

Respuesta v1: conversation_id, mode, through_message_id, latest_transition
(solo ID/modos/fecha), messages, truncated, history_is_authorization=false.
Cache-Control: private, no-store. Vary: Authorization. Sin CORS público.

Historial anterior al mensaje ancla, sin repetir el mensaje actual:
  - hasta 50 mensajes de texto, 2000 caracteres/mensaje, 24000 totales;
  - orden por fecha de registro y UUID, no por occurred_at manipulable;
  - user/bot received o sent; human_agent SOLO sent;
  - NO sending/failed, archivos, metadata, detalle de error, IDs/nombres internos
    de agentes, credenciales, notas del CRM ni datos de otras conversaciones.
  - mode human/pending: respuesta sin historial, el agente no se invoca.
  - conversación o ancla desconocida: 404, no crea ninguna fila.

Flujo preparado:

      false → Delete Buffer 1 (no envío)

Los HTTP GET nuevos reutilizan la referencia de credencial existente y el alcance
del GET mode. Timeout 3s, sin reintentos, error → detener ejecución, NO continuar
con memoria antigua. El mensaje actual se lee del trigger propio, NO del texto
combinado de un buffer global. Las preguntas previas del MISMO hilo ya vienen en
el historial. Todos los IDs de nodos originales y sus credenciales se conservan.

El historial se serializa como datos JSON en el mensaje al agente. La política
estática se añade al system prompt: recordar datos/respuestas, evitar repreguntas,
revisar herramientas de lectura para hechos actuales y pedir consentimiento
actual y específico para acciones. Nunca convierte un sí antiguo en autorización.
Validación de versión, conversación, ancla, modo, tamaño y esquema antes del agente.

LÍMITES IMPORTANTES

- El aislamiento y los límites de lectura son controles de servidor, probados.
- Entender preguntas pendientes/no repetir es comportamiento del LLM: el ensamblado
  del prompt no demuestra por sí solo que el modelo obedecerá. Requiere regresión
  manual/sintética del modelo en el banco inactivo y después el chat autorizado.
- Revalidar el modo justo antes del envío reduce carreras; NO es una exclusión
  atómica entre ese GET y Meta, ni bloquea una herramienta de escritura que el LLM
  ya hubiera llamado mientras cambiaba el modo. No se anuncia como solución a
  todas las carreras. Las herramientas/citas mantienen sus controles actuales.
- El buffer legado usa una clave de WhatsApp no cualificada. El parche no la
  consume como texto del agente, pero no corrige posibles colisiones de debounce
  entre workflows que compartan esa tabla; eso requiere revisar su esquema y
  migrar todas sus lecturas/escrituras coordinadamente en otro cambio.
- Un humano marcado sent fue aceptado por el canal; no se afirma confirmación de
  lectura del destinatario. Los fallidos no se presentan como algo que vio.
- Los mensajes largos/historial antiguo pueden truncarse: el bot no debe fingir
  disponer de toda la conversación.
